CoreOps — Trust Boundaries & Data Flow

Four places CoreOps stops trusting what it's holding

Data enters from three real external services and a real human, crosses four points where its trust level changes, and only reaches a real action if it survives all four. This is that path, drawn as it actually runs — not as an inventory of components.

What each boundary actually enforces

IDENTITY BOUNDARY
An anonymous browser becomes a verified operator only after a real login — a password checked against a scrypt hash, a session id the page's own JavaScript can't read (HttpOnly). Before this existed, "approved by quincy" was a hardcoded string nobody had actually verified.
EXTERNAL-SERVICE BOUNDARY
Nothing from Azure SQL, Claude, or ntfy is trusted on arrival. SQL reads are parameterized, never string-built; every row is checked against a schema before it's allowed to become evidence; a live query and a fixture fallback are always tagged honestly, never blended.
RENDER BOUNDARY
Anything that reaches the page goes through textContent or an explicit escape function — never raw innerHTML. This is the one a real audit caught failing: a handful of API responses were being concatenated into the page unescaped, including one that echoed back whatever a caller sent it. Fixed and verified by actually running the exploit payload through the real code path.
ACTION BOUNDARY
The guardrail — a pure, deterministic function every proposed action must pass: linked to real evidence, an allowed reversible type, and a genuine human approval record. This is the boundary between "the system has an opinion" and "the system did something," and it's the one no other boundary is allowed to substitute for.
