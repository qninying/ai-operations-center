CoreOps — Solution Architecture Capstone

An enterprise-grade AI Operations Dashboard for SQL Server, SSIS, SSRS, and Windows servers — an intelligent command center that detects, diagnoses, and proposes remediations for operational incidents, with every production-affecting action gated behind a real human approval. Built solo, end to end, with Claude Code as an AI pair, in 8 real calendar days.

This document is the architecture-and-evidence capstone for that build: the real decision log, the real requirement-to-story trace, the real test and live-verification record, and the real delivery timeline — everything traces to a file, a commit, or a test run in github.com/qninying/ai-operations-center. Nothing here is illustrative or hypothetical unless explicitly labeled as such.

System Architecture

Seven real layers, one golden thread

CoreOps maps onto the standard 7-layer reference architecture for AI systems. Every box below is a real module in this repo as of 2026-08-24, not a target diagram — the full write-up lives in 7-layer-architecture-mapping.md, with companion diagrams in architecture-summary.html and trust-boundaries.html. This section condenses that mapping; it doesn't replace it.

The golden thread: a correlation ID is generated once, when a monitoring cycle starts (Layer 03), carried through the reasoning result (04), the guardrail evaluation (02), and recorded at every step by Layer 07 — so GET /api/audit?correlationId= reconstructs one entire incident, from first evidence to the human decision, as one connected trail rather than scattered fragments.
Target vs. built, stated plainly: project-blueprint/architecture.md names a larger target stack (Kafka, TimescaleDB, Faust, PostgreSQL, Telegraf) for a future, higher-scale version. None of that is implemented today. The real, running system holds its state in-process and in an append-only JSONL file (per ADR-005) — a deliberate scale-appropriate choice, not an oversight, and it's disclosed here rather than left for a reader to discover independently.
Architecture Decision Log

7 real ADRs — every one naming what it rejected

All seven were written and closed inside the same 8-day build, most on 2026-08-23/24 in response to a documented trust-posture assessment. Each links a real decision to a real, cited alternative it beat, and to a real verification step — not just the choice made.

ADR-001 Transport selection for the MCP Tool Gateway Implemented

Decision: run two transports for two consumers — STDIO kept as a local, dev-only entry point; StreamableHTTP added for the deployed Tool Gateway, gated by a real bearer token (auth/apiToken.ts).

Rejected: STDIO alone (no cross-host reachability, no multi-client concurrency) · SSE / legacy HTTP ("not a serious contender" — the MCP spec is deprecating it in favor of StreamableHTTP).

Verified: a real random bearer token was generated; unauthenticated and wrong-token requests returned real 401s; a real MCP handshake (initialize + tools/list) returned both real tools. 167 tests passing at time of writing; tsc --noEmit clean.

ADR-002 Unify correlation IDs across the audit trail Implemented

Decision: extend guardrails/auditLog.ts with a SystemEventAuditEntry type and wire every mcp-server service through one correlation ID per real-world incident, instead of building a second audit system.

Rejected: a second, parallel audit/telemetry system — explicitly named as the first decision driver to avoid.

Verified: a real /api/recommendation call at 55% confidence produced three real entries under one correlation ID — recommendation_data_access, escalation_triggered, and a real operator_notification_delivered ntfy dispatch.

ADR-003 Session-based authentication over JWT Implemented

Decision: in-process session store, HttpOnly + SameSite=Strict cookies, scrypt password hashing. Followed a real trust-boundary audit that found every dashboard route reachable by anyone, and a hardcoded approver comparison that could never fail.

Rejected: JWT — revocation would need a server-side blocklist (defeating statelessness); single-process deployment means JWT's core advantage buys nothing; an XSS audit had just found and fixed real unescaped innerHTML sinks, and a JWT in localStorage sits in that same exposure class. This was an explicit user decision point ("JWT or session-based?"), not a default.

Verified: every route except /, /health, /login, POST /api/login, POST /api/logout now runs through requireSession(); built, unit-tested, live-verified.

ADR-004 Serve the built React console from mcp-server itself Implemented

Decision: serve the compiled console at GET /console and root-relative /assets/* from the same Node process, with a path-traversal-guarded static file resolver.

Rejected: a base: '/console/'-prefixed build (higher cross-file coupling) · a reverse proxy / nginx ("this repo has zero reverse-proxy config today" — a legitimately bigger decision than this one) · leaving it unresolved, dev-proxy only ("not a decision, it's declining to make one").

Verified: npm run build-console was run for real; the emitted dist/index.html was inspected directly to confirm root-relative asset paths.

ADR-005 Append-only JSONL persistence for the audit trail, with size-based rotation Implemented

Decision: the audit log gains a persistTo path, rehydrates in memory on startup, appends synchronously, and rotates into numbered archive segments (default 5,000 lines/segment) — never deletes. Followed a trust-posture assessment that found the entire audit trail lived only in an in-memory Map, erased on every restart.

Rejected: SQLite ("no SQLite/database dependency exists in this repo today" — a new persistence idiom) · defer/document only ("the user explicitly asked for this fixed, not just re-documented") · time-based or delete-after-N-days rotation ("a burst of activity would produce one huge daily file just the same"; deletion "rejected outright" for a governance record).

Verified: proposed and approved a real remediation, killed the running server process outright, restarted it, confirmed both audit entries were still retrievable. Rotation was verified against a copy of the real, running system's actual audit-log.jsonl — 48 real entries at the time — forced a rotation with a small threshold, confirmed byte-for-byte archive integrity and correct continuity to 49 entries.

ADR-006 Real TOTP-based MFA, replacing a hardcoded mfa: true Implemented

Decision: hand-rolled TOTP (RFC 6238) via node:crypto, required on every login. Because login itself now requires TOTP, every session is inherently MFA-verified by construction — no separate session-level MFA flag was needed, and the guardrail's mfa check "stops being a hardcoded lie."

Rejected: OTP delivered via ntfy.sh (weaker; depends on delivery availability) · WebAuthn / passkeys ("disproportionate complexity for what this system actually needs today").

Verified against the published RFC 6238 Appendix B SHA-1 test vectors, plus live: missing code → real 400; wrong code → real 401; correct code → real 200 + cookie; replaying the exact same code → real rejection, even with the correct username and password. 17 new tests.

ADR-007 A real second approver identity Implemented

Decision: a named second user (userDirectory.ts), each configured user with their own independent TOTP verifier state. Closed two gaps at once: the backup approver was a hardcoded string with no real login, and the escalation-timeout check existed and was tested but was never actually called from production code.

Rejected: a general N-user credential file — "the escalation model has no third role to justify it," called out explicitly as premature abstraction against this repo's own conventions.

Verified live, on the real clock: proposed a remediation as the primary approver, waited the real 15-minute decision window, logged in as the real backup approver and decided the item, then confirmed the primary could no longer decide it (403 UNAUTHORIZED_DECIDER). The full 4-event sequence — hitl_enqueued → hitl_escalated → hitl_decision → hitl_decision_rejected — is in the real audit log.

Real bugs the tests and live verification actually caught before shipping

WhereWhat was found live
STORY-006 · SQL Server DMVSorting by cpu_time DESC alone silently buried a genuine blocking session (near-zero CPU by definition) under 40-50+ Azure background system sessions. Fixed by excluding status = 'background' and sorting any blocked session first, guarded by a regression test.
STORY-007 · Azure Blob StorageVerified against a real, live account (coreopsdiagnostics/diagnostics) — a real read produced an honestly low-confidence recommendation; a nonexistent container produced a real 503, not a hang or a fabricated result.
STORY-008 · Continuous monitoringA cold-starting Azure SQL free-tier instance took ~30s to respond against a 10s polling interval — overlapping cycles piled up and tripped the shared circuit breaker on a false alarm. Fixed with an in-flight guard, covered by a regression test.
STORY-009 · EscalationBoundary-tested at exactly 59% vs. 60% confidence. Live-verified on the real SQL path: a quiet database (20% confidence) correctly escalated; a real seeded blocking scenario (75% confidence) correctly did not.
STORY-010 · NotificationVerified live end-to-end — a real escalation triggered a real HTTP POST to ntfy.sh, confirmed by polling ntfy's own API for the delivered push (correct title, incident summary, operator name).
STORY-011 · RollbackA denial's explanation text was keyed as reason, silently colliding with and overwriting the categorical denial code (also reason) in the same log line — caught by tests before shipping, renamed to detail.
ADR-006 · TOTP MFAVerified against published RFC 6238 test vectors; live-verified that replaying an already-used code is rejected even with the correct password.
ADR-007 · Second approverVerified on the real wall clock — a genuine 15-minute wait, a real escalation to a real second human, and a real lockout of the original approver afterward.
REQ-014 · Confidence thresholdsLive-verified across three separate real subprocesses: default behavior unchanged, a real override genuinely changes escalation gating, and a malformed value throws at import time instead of silently corrupting the threshold and disabling the gate it controls.
REQ-017 · Cross-system correlationLive-verified against the real running server that both sources can be genuinely unavailable for two different real reasons at once (SQL: Azure quota exhausted; SSRS: not configured) — the route correctly returned a real 503, with two distinct per-source entries under one correlation ID in the real durable audit log, not a single collapsed failure.

Operating Footprint & Cost Posture

What this actually costs to run — stated honestly

There is no dollar-figure cost model anywhere in this repo, and this document doesn't invent one. What follows is only what's real and citable.

ComponentReal, cited fact
