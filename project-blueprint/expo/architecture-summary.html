Architecture Summary — CoreOps

The system can investigate.
It cannot act without you.

CoreOps is an AI operations command center for SQL Server, SSIS, SSRS, and Windows Server infrastructure — it watches for incidents, explains root cause with Claude, and proposes fixes. Every proposal stops at a real, enforced human-approval gate before anything touches production.

210 tests, all passing Live-verified, not just unit-tested Real Azure SQL, Blob Storage, Claude API Zero fabricated data — honest fallback when a source is down
The problem

Root-causing a SQL Server incident means manual cross-referencing, hours after the fact.

A job fails, or a report comes back empty. Someone has to correlate job logs, blocking sessions, and downstream reports across a dozen tools to explain why — usually well after it mattered. CoreOps watches continuously, correlates related signals, and asks Claude to explain root cause from live evidence, not a static runbook.

How it works

Detection to decision, in one traceable chain

Every step below shares one correlation ID — the whole story for a single incident is reconstructable after the fact, not just each step in isolation.

01

Continuous monitoring detects it

Polls SQL Server's live session state (sys.dm_exec_requests) on an interval. A genuinely blocked session — not noise — triggers the chain.

02

Claude explains root cause

A real model call over the actual evidence rows, not a canned response — returns a root-cause explanation and a confidence score.

03

Low confidence escalates

Below 60%, the system notifies the on-call operator by real push delivery rather than presenting a guess as settled.

04

A remediation is proposed — and blocked

The guardrail checks it's evidence-linked, of an allowed reversible type, and human-approved. Missing approval fails it, every time, no exceptions.

05

A signed-in operator decides

Approve executes the one real reversible action wired up; reject leaves everything untouched. Both are logged under the same identity that logged in.

The guardrail

"An action gets blocked because it lacks approval — not because the system can't figure out what to do, but because it isn't allowed to decide alone."

One rule outranks everything else in this design

Every proposed remediation passes through a pure, deterministic check before an execution path is even reachable: it must be linked to real incident evidence, of an allowed reversible action type, and carry a genuine human approval record. This isn't a policy comment enforced by convention — it's a function every code path runs through, and it's what a login system exists to make meaningful: the approver on record is the operator who actually signed in, verified by a password hash, not a name string nobody checked.
